## 1. Назначение ML‑сервиса

ML‑сервис отвечает за:

- разовую и повторную загрузку сырых CSV из Kaggle (данные про‑матчей 2016–2026, фактически используются 2024–2025), их очистку и агрегацию;
    
- интеграцию с данными игрока/тренера из Steam/Dota (через `steam_id`/`dota_account_id` и OpenDota/аналогичные API);
    
- расчёт общих статистик и детальных срезов (по героям, ролям, матчам);
    
- построение фичей на основе **эталонного игрока** для каждой конфигурации (`mmr_band`, герой, роль) и вычисление отклонений игрока от эталона;
    
- вычисление «псевдо‑MMR» (MMR‑аналога) для игроков без официального рейтинга и/или с закрытым профилем;
    
- выдачу структурированных данных core‑сервису: фичи, агрегаты, рекомендации по тренерам.
    

---

## 2. Стек и инфраструктура

- Язык: Python 3.10+
    
- Framework API: FastAPI
    
- ML/данные: pandas, numpy, scikit‑learn (для оценок / MMR‑аналога), joblib для сохранения моделей.
    
- БД: Postgres (схема `ml`), файловое хранилище CSV (volume/директория).
    
- Источники данных:
    
    - Kaggle dataset «Dota 2 Pro League Matches 2016–2026» (таблицы матчей, игроков, героев, результаты);
        
    - Dota/Steam‑API через core (данные матчей конкретного игрока/тренера);
        
- Контейнер: отдельный Docker‑контейнер `ml-service`.
    

---

## 3. Источники данных и загрузка Kaggle CSV

## 3.1. Структура CSV (по Kaggle‑датасету)

Точное содержание файлов может отличаться, но базово у Kaggle‑датасета есть:

- таблицы матчей (match‑уровень):
    
    - `match_id`, `start_time`, `duration`, `league`, `radiant_win`, `radiant_team`, `dire_team`, `patch` и т.п.
        
- таблицы игроков/героев в матче (player‑уровень):
    
    - `match_id`, `player_slot`, `hero_id`, `kills`, `deaths`, `assists`, `gold_per_min`, `xp_per_min`, `last_hits`, `denies`, `hero_damage`, `tower_damage`, `lane`, `lane_role`, `position`, и т.п.
        

Точное описание колонок фиксируется в приложении к ТЗ после анализа скачанных CSV (в коде — маппинг имён колонок к внутренним полям).

## 3.2. Требования к загрузке CSV

- Админ через интерфейс core‑сервиса передаёт путь к директории с CSV (например, `/data/dota_kaggle/2024`, `/data/dota_kaggle/2025`).
    
- ML‑сервис должен уметь:
    
    - по одному вызову загрузить **все CSV** из указанной директории;
        
    - определить тип файла по имени (например, `matches.csv`, `players.csv` и т.п.) — имена одинаковы для разных годов/директорий;
        
    - добавить/обновить данные в Postgres (`ml_raw_matches`, `ml_raw_players` и т.п.), помечая источник (год/директория).
        
- При успешной загрузке вернуть статус и количество загруженных записей по каждой таблице; ошибки (битые строки, дубликаты) логируются.
    

## 3.3. Таблицы для сырых данных (упрощённо)

- `ml_raw_matches` — match‑уровень;
    
- `ml_raw_players` — player‑уровень (10 строк на матч);
    
- опционально: `ml_raw_heroes` (метаданные по героям).

## 4. Обработка данных игрока: открытый/закрытый профиль

## 4.1. Открытый профиль

Если профиль Steam/Dota **открыт** и привязан (`steam_id`, `dota_account_id` есть):

- core‑сервис предоставляет ML‑сервису идентификатор игрока (`steam_id`/`dota_account_id`) и/или уже скачанную статистику (через OpenDota и т.п.);
    
- ML‑сервис:
    
    - получает список последних матчей игрока (через API или из локального кэша);
        
    - рассчитывает фичи для каждого матча и агрегаты по игроку (см. раздел 6);
        
    - оценивает «MMR‑аналог» по статистике (см. 5.2).
        

## 4.2. Закрытый профиль или отсутствие данных

Если:

- профиль закрыт (нет доступа к статистике матчей);
    
- профиль не привязан вообще (нет `steam_id`/`dota_account_id`);
    
- игр мало (< X матчей или < 10 часов в Dota);
    

то ML‑сервис должен:

- **установить MMR‑аналог на минимальное значение** (условный нижний порог, например, 1000 или отдельный класс «BEGINNER»);
    
- считать, что игрок **не имеет полноценных фактических фичей**;
    
- использовать только данные, введённые вручную:
    
    - выбранный герой/герои;
        
    - выбранная роль;
        
    - желаемый ранг;
        
    - цели (`training_goals`).
        

Это явно прописывается в ТЗ:

> «Если данных матчей недостаточно (закрытый профиль, отсутствующие данные или менее 10 часов игры), ML‑сервис не строит MMR‑аналог и использует минимальный уровень навыка, опираясь только на ручной ввод игрока.»

## 5. MMR‑аналог и конфигурация эталонного игрока

## 5.1. Конфигурация (configuration) эталонного игрока

Эталонный игрок определяется для каждой конфигурации:

- `mmr_band` — диапазон MMR‑аналога (например, 0–2000, 2000–4000, 4000–6000, 6000+);
    
- `hero_id` — конкретный герой;
    
- `role` — позиция (POS1–POS5 или lane_role).
    

Таким образом, для каждой тройки (`mmr_band`, `hero_id`, `role`) рассчитывается **эталон** по ключевым метрикам:

- средний GPM/XPM;
    
- средний KDA, deaths per 10 min;
    
- средний урон по героям/строениям;
    
- средняя длина игры;
    
- средний winrate;
    
- другие derived фичи (см. ниже).
    

## 5.2. Оценка MMR‑аналога игрока

Для игрока, у которого есть достаточно матчей:

- собираются статистики по его матчам (GPM, XPM, KDA, winrate, длительность, роли, герои);
    
- в качестве MMR‑аналога можно использовать:
    
    - либо регрессионную модель (например, RandomForest/GradientBoosting) обученную на Kaggle‑данных, где таргет — известный MMR/ранг, а признаки — агрегаты по игроку;
        
    - либо более простую эвристику (перцентили по GPM/XPM/KDA относительно Kaggle‑выборки).
        

Для ТЗ достаточно зафиксировать:

> «MMR‑аналог (estimated_mmr) оценивается как функция агрегированных метрик игрока (GPM, XPM, KDA, winrate, длительность игры, роль/герой) по отношению к распределениям этих же метрик у профессиональных игроков из Kaggle‑датасета. В отсутствии официального MMR используется эта оценка.»

## 6. Фичи и агрегаты (feature engineering)

Фичи делятся на:

- **базовые** (прямо из матчей);
    
- **агрегированные по игроку**;
    
- **derived (производные)** — сравнение с эталоном, перцентили и индексы.
    

## 6.1. Базовые матч‑фичи (на уровне одного матча)

Для каждого матча игрока:

- `duration_minutes` — длительность;
    
- `kills`, `deaths`, `assists`;
    
- `kda` = (kills+assists)/max(1,deaths)(kills+assists)/max(1,deaths);
    
- `gpm` (gold_per_min);
    
- `xpm` (xp_per_min);
    
- `last_hits`, `denies`;
    
- `hero_damage`, `tower_damage`;
    
- `win` (0/1);
    
- `hero_id`;
    
- `role` (POS1–POS5 / lane_role);
    
- временные фичи (если есть): GPM/XPM по минутам → тренды.[](https://octopuscabbage.github.io/machine-learning/2016/07/31/dota-2-data-science.html)​
    

## 6.2. Агрегированные фичи по игроку

По всему набору матчей (или последним N матчей):

- общее количество матчей;
    
- количество часов (сумма `duration_minutes`);
    
- суммарный winrate;
    
- средний/медианный GPM, XPM, KDA;
    
- распределение по ролям (% матчей на POS1–POS5);[](https://academicworks.cuny.edu/cgi/viewcontent.cgi?article=5489&context=gc_etds)​
    
- распределение по героям (топ герои по количеству игр и winrate);
    
- средняя длительность игры;
    
- частота ранних/поздних концовок (короткие/долгие игры).
    

## 6.3. Производные фичи (относительно эталона)

Для каждой конфигурации (`mmr_band`, `hero_id`, `role`):

- `gpm_delta` = gpmplayer−gpmbaselinegpmplayer−gpmbaseline;
    
- `xpm_delta` = xpmplayer−xpmbaselinexpmplayer−xpmbaseline;
    
- `kda_delta`;
    
- `deaths_per_min_delta`;
    
- `lh_10min_delta` (если есть);
    
- перцентили: `gpm_percentile`, `xpm_percentile`, `kda_percentile` против распределений Kaggle.
    

Дополнительные индексы:

- **Lane CS Quality**: отношение добивания крипов к эталону на линии.
    
- **Vision Index**: отношение поставленных вардов/к покупкам детекшена к эталону (при наличии соответствующих колонок).
    
- **Teamfight Impact**: доля урона по героям относительно команды.
    

Группировки:

- по роли;
    
- по герою;
    
- по патчу/времени;
    
- по длительности матча.
    

Эти фичи используются:

- для блока статистики (`/stats/overview`, `/features`);
    
- в моделях оценки MMR‑аналога;
    
- в матчмейкинге тренеров (сравнение слабых/сильных сторон игрока и специализации тренера).

## 7. API ML‑сервиса

## 7.1. `POST /ml/admin/load-kaggle-data`

**Назначение:** разовая/повторная загрузка CSV с Kaggle из указанной директории (через админ‑кабинет).

**Вход (JSON):**

json

`{   "directory_path": "/data/dota_kaggle/2025" }`

**Шаги:**

1. Проверить права (доступ только у ADMIN).
    
2. Найти все CSV в директории.
    
3. Для известных имен файлов (`matches.csv`, `players.csv` и т.п.) запустить парсинг:
    
    - загрузить в временные таблицы;
        
    - дедуплицировать/обновить основные таблицы `ml_raw_matches`, `ml_raw_players`;
        
    - вести счётчик загруженных/пропущенных строк.
        
4. Вернуть статус.
    

**Ответ:**

json

`{   "status": "success",  "files_processed": [    { "file": "matches.csv", "rows_inserted": 12000 },    { "file": "players.csv", "rows_inserted": 120000 }  ] }`

---

## 7.2. `POST /ml/match-coaches`

(Контракт уже отражён в core, здесь формализуем с точки зрения ML.)

**Вход (JSON):** как описано в core‑секции (профиль игрока + данные заявки).

**Шаги:**

1. Если есть `steam_id`/`dota_account_id` и профиль открыт:
    
    - загрузить/обновить последние матчи игрока;
        
    - посчитать фичи и MMR‑аналог.​
        
2. Если данных нет/мало:
    
    - задать минимальный MMR‑аналог;
        
    - использовать только ручные поля.
        
3. Сопоставить профиль игрока и профили тренеров (данные тренера из Steam/Dota по аналогичной схеме или упрощённо):
    
    - выбрать тренеров с подходящим `mmr_band`, героями/ролями, специализацией;
        
    - рассчитать score совместимости (роль, герой, опыт, стиль, успех с похожими игроками).
        
4. Сформировать `player_assessment` и `recommended_coaches` (как в core‑контракте).
    
5. Сохранить результаты в таблицах `ml_player_analyses` (например) и вернуть `ml_analysis_id`.
    

**Выход (JSON):**

json

`{   "ml_analysis_id": "analysis_abc123",  "player_assessment": { ... },  "recommended_coaches": [ ... ],  "ai_coach_suggestion": { ... } }`

---

## 7.3. `GET /ml/player-analysis/{ml_analysis_id}`

**Назначение:** отдать полный анализ игрока для статистики и фичей.

**Выход (JSON):**

json

`{   "ml_analysis_id": "analysis_abc123",  "summary": { ... },      // для /stats/overview  "trends": { ... },  "roles": { ... },  "heroes": { ... },  "comparisons": { ... },  "features": { ... },     // для /features  "weaknesses_ranked": [ ... ],  "strengths_ranked": [ ... ] }`

---

## 7.4. Таблицы ML‑сервиса (агрегаты)

Минимум:

- `ml_player_analyses` — хранит `ml_analysis_id`, ссылку на `player_profile_id`, MMR‑аналог, агрегаты и фичи (jsonb).
    
- `ml_coach_stats` — агрегаты по тренерам (для матчмейкинга).
    
- `ml_kaggle_baselines` — предрасчитанные эталоны по конфигурациям (`mmr_band`, `hero_id`, `role`).
