## 1. Назначение и цели проекта

Проект представляет собой веб‑сервис подбора тренеров по Dota 2 и AI‑тренера, который:

- анализирует игры игрока (через Steam/Dota/OpenDota и Kaggle‑данные);
    
- строит профиль игрока (фактический уровень + его цели и желаемые роли);
    
- подбирает живого тренера и/или AI‑коуча под эти параметры;
    
- предоставляет личный кабинет игрока, тренера и административный интерфейс;
    
- визуализирует статистику и детальные фичи игрока по сравнению с эталонными игроками.
    

Основная цель — учебный, но расширяемый продукт: система должна быть развёртываема, расширяема по сервисам и готова к интеграции с выбранной LLM‑моделью.

---

## 2. Общая архитектура

Проект реализован как набор сервисов:

- Auth‑сервис — аутентификация и управление пользователями/ролями;
    
- Core‑сервис (backend/BFF) — основной домен: профили, заявки, расписание, статистика, админка;
    
- ML‑сервис — загрузка и обработка данных, расчёт фичей, MMR‑аналога, эталонов и рекомендаций;
    
- LLM‑сервис — генерация текстовых советов и чат‑интерфейс (готовится к интеграции с LLM);
    
- Frontend — React‑приложение (личные кабинеты, графики, админ‑панель).
    

Все сервисы работают в Docker‑контейнерах, взаимодействуют по HTTP/REST, используют общую БД Postgres (логически разделённую по доменам).

## 4. Сервисы и их ответственность

## 4.1. Auth‑сервис

**Роль:** отдельный сервис аутентификации и управления пользователями.

Функциональность:

- Регистрация по логину/email + паролю (с подтверждением пароля).
    
- Хранение пользователей (`auth_users`), ролей (`auth_roles`: ADMIN, PLAYER, COACH), сессий (`auth_sessions`).
    
- Выдача и обновление JWT (access + refresh), хранение refresh‑токенов.
    
- Логин через Steam: привязка Steam‑аккаунта (`auth_providers`) и последующий вход.
    
- Подключение Steam к уже существующему аккаунту (`POST /auth/link-steam`).
    
- Logout одной сессии и всех сессий (отзыв refresh‑токенов).
    

Auth не знает ничего о профилях игроков/тренеров — только о пользователях, ролях и провайдерах.

## 4.2. Core‑сервис

**Роль:** основной доменный backend (BFF/оркестратор).

Функциональность:

- Личный кабинет с учётом роли (PLAYER, COACH, ADMIN).
    
- Профиль игрока (`player_profiles`):
    
    - фактические данные: `steam_id`, `dota_account_id`, `actual_rank_tier`, `actual_roles`;
        
    - желаемые параметры: `desired_rank_tier`, `desired_roles`, `training_goals`, `about`.
        
- Профиль тренера (`coach_profiles`): роли, герои, MMR‑оценка, опыт, ставка, описание.
    
- Заявки (`training_requests`): создание, просмотр, отмена, связь с анализом ML и рекомендациями тренеров.
    
- Тренировочные сессии (`training_sessions`): планирование, перенос, отмена, завершение.
    
- Отчёты тренера и отзывы (`coach_reviews`).
    
- Статистика и фичи игрока (`/stats/overview`, `/features`) — интеграция с ML‑сервисом.
    
- Чат с LLM‑тренером (`/ai/chat`, `/ai/history`) — интеграция с LLM‑сервисом.
    
- Админ‑панель: просмотр логов (`core_action_logs`), пользователей, профилей, базовой статистики по сервису; безопасный read‑only просмотр данных БД через заранее определённые запросы.[](https://www.scitepress.org/publishedPapers/2025/133910/pdf/index.html)​
    

Core выступает единственной точкой входа для фронта, проверяет JWT из Auth и реализует бизнес‑авторизацию (кто что может делать).

## 4.3. ML‑сервис

**Роль:** аналитическое ядро.

Функциональность:

- Загрузка Kaggle‑CSV через admin‑интерфейс (путь к директории) и сохранение сырых данных в `ml_raw_matches`, `ml_raw_players` и др.
    
- Расчёт эталонных игроков по конфигурациям (`mmr_band`, герой, роль) на основе Kaggle.
    
- Получение и анализ матчей конкретного игрока (через Steam/OpenDota): фичи матча, агрегаты по игроку.
    
- Оценка MMR‑аналога игрока по его статистике относительно распределений эталона; в случае отсутствия данных/закрытого профиля — минимальный уровень.
    
- Формирование фичей, агрегатов, сравнений с эталоном (см. ML_SPEC).
    
- Matchmaking‑API: рекомендует тренеров для игрока с учётом ролей, героев, MMR‑уровня, целей и предыдущих результатов тренеров.
    

ML не занимается UI и не знает деталей фронта — отдаёт структурированный JSON для core.

## 4.4. LLM‑сервис

**Роль:** сервис для работы с LLM (пока заглушка, подготовленная к интеграции).

Функциональность (целевое состояние):

- Принимает от core структурированный контекст игрока:
    
    - summary и фичи из ML‑сервиса (слабые/сильные стороны, цели);
        
    - вопрос/сообщение игрока.​
        
- Формирует промпт под выбранную модель (OpenAI/Anthropic/др. или через LLM‑прокси).
    
- Возвращает:
    
    - краткое резюме;
        
    - структурированный план действий (по шагам, по темам);
        
    - полный текст ответа.
        
- Сохраняет историю запросов/ответов (`llm_requests`, `llm_responses`) для аналитики.
    

На момент запуска может быть реализован в виде API‑заглушки (фиксированный/шаблонный ответ), с чётким контрактом, чтобы потом заменить реализацию на реальную LLM.

## 4.5. Frontend

**Роль:** UI‑слой для всех ролей.

Функциональность:

- Публичные страницы: лендинг, логин, регистрация, базовая информация.
    
- Личный кабинет игрока: профили, список тренеров, заявки, расписание, статистика, фичи, чат с LLM‑тренером.
    
- Личный кабинет тренера: профиль, расписание, заявки, отчёты, отзывы.
    
- Админ‑панель: пользователи, логи, статистика, Kaggle‑импорт.
    
- Общий UI‑тулкит (дизайн‑система) из переиспользуемых компонентов.
    

Фронт не имеет прямого доступа к БД и соблюдает базовые практики безопасности (см. FRONTEND_SPEC).

---

## 5. Взаимодействие между сервисами

- Frontend → Core/Auth/ML/LLM: только HTTP‑запросы по защищённому протоколу (HTTPS).
    
- Core → Auth: верификация JWT, получение роли/данных пользователя (`/auth/me`, `/auth/introspect`).
    
- Core → ML: создание заявок на анализ и подбор (`/ml/match-coaches`), получение анализов игроков (`/ml/player-analysis/{id}`), вызов админ‑импорта Kaggle.
    
- Core → LLM: запрос советов и истории чата.
    

Доступ к базе данных:

- Auth владеет только таблицами `auth_*`.
    
- Core владеет `core_*`.
    
- ML владеет `ml_*`.
    
- LLM — `llm_*`.
    

Другие сервисы не ходят напрямую в чужие таблицы, только через API и только core фронтирует всё для клиентской части.

## 6. Роли и политика доступа (сводно)

- `PLAYER`:
    
    - доступ к своим профилям, заявкам, сессиям, статистике, чату LLM;
        
    - не видит чужие данные, кроме публичных профилей тренеров.
        
- `COACH`:
    
    - доступ к своему профилю, расписанию, сессиям, отзывам;
        
    - ограниченный доступ к данным игроков, с которыми у него есть сессии.
        
- `ADMIN` (технический аккаунт):
    
    - просмотр логов действий, основных таблиц (read‑only интерфейс);
        
    - управление аккаунтами (блокировка, смена ролей);
        
    - запуск загрузки Kaggle‑данных;
        
    - доступ к агрегированной статистике по сервису.
        

Роли задаются и хранятся в Auth, политика проверки прав реализуется в Core/других сервисах.

## 7. Нефункциональные требования

- **Развёртываемость:**
    
    - каждый сервис в отдельном Docker‑контейнере;
        
    - docker‑compose для локального запуска;
        
    - возможность разнести сервисы по контейнерам/подам в будущем.
        
- **Производительность:**
    
    - core‑эндпоинты матчмейкинга и статистики должны отвечать < 1–2 сек при разумном размере данных;
        
    - ML‑операции могут быть тяжелее, но для UX желательно кешировать результаты анализов.
        
- **Масштабируемость:**
    
    - сервисы stateless (auth, core, ml, llm) могут масштабироваться горизонтально;
        
    - heavy‑операции ML и LLM можно вынести в фоновую обработку/очереди (целевое состояние).
        
- **Безопасность:**
    
    - HTTPS, JWT, отсутствие прямого доступа фронта к БД;
        
    - нет ввода произвольного SQL через интерфейс;
        
    - базовая защита от XSS/CSRF на фронте и строгая валидация/авторизация на бэке.
        
- **Логирование и аудит:**
    
    - core‑сервис ведёт `core_action_logs`;
        
    - ML/LLM ведут свои логи операций (для отладки и улучшения моделей).[](https://www.scitepress.org/publishedPapers/2025/133910/pdf/index.html)​
