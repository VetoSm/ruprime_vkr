## 1. Назначение и стек фронтенда

- Фронтенд — SPA/SSR‑приложение на React, использует только HTTP‑API core/auth/ML/LLM, **не имеет прямого доступа к БД**.
    
- Основные задачи:
    
    - личный кабинет игрока, тренера, технического аккаунта;
        
    - визуализация статистики и фичей (графики, таблицы);
        
    - интерфейсы для заявок, расписания, чата с LLM;
        
    - админ‑интерфейс (логи, просмотр данных, управление аккаунтами).
        

Рекомендуемый стек:

- React + React Router (или Next.js, если хочешь SSR/SEO проще для лендинга);
    
- UI‑кит (либо готовый, либо собственный дизайн‑систем/тулкит);
    
- Chart‑библиотека (Recharts/Chart.js/echarts) для графиков;
    
- Axios/RTK Query/SWR для запросов к API.

## 2. Страницы и маршруты

## 2.1. Публичная часть

- `/` — лендинг (рекламная страница, позже опишем отдельно).
    
- `/login` — страница входа (email/логин + пароль).
    
- `/register` — регистрация.
    
- `/privacy`, `/terms` — базовые юридические страницы (по минимуму).
    

## 2.2. Личный кабинет (PLAYER)

Все приватные маршруты защищены: при отсутствии access‑токена происходит редирект на `/login`.

- `/dashboard` — обзор (использует `/me/overview`):
    
    - карточки: текущий ранг/оценка, ближайшие тренировки, активные заявки, статус подключения Steam/Dota.
        
- `/profile/player`
    
    - форма редактирования поля анкеты: `desired_rank_tier`, `desired_roles`, `training_goals`, `about`;
        
    - отображение фактических данных (read‑only): `actual_rank_tier`, `actual_roles`, `steam_id`, `dota_account_id`.
        
- `/coaches`
    
    - список тренеров (фильтры по роли, рангу, цене);
        
    - карточка тренера → `/coaches/:id` (профиль тренера, опыт, отзывы).
        
- `/matchmaking`
    
    - форма создания заявки (`desired_role`, `focus_area`, `use_ai_coach`);
        
    - отображение рекомендованных тренеров (после ответа core).
        
- `/requests`
    
    - список заявок, статусы;
        
    - действия: отмена, выбор тренера, переход к созданной сессии.
        
- `/schedule`
    
    - календарный вид/таблица предстоящих и прошедших тренировок (core `/training-sessions/my`).
        
- `/stats`
    
    - вкладка «Общая статистика» (использует `/player/{id}/stats/overview` → графики и карты);
        
    - вкладка «Фичи/детальный анализ» (использует `/player/{id}/features`).
        
- `/ai-chat`
    
    - чат с LLM‑тренером (история + форма отправки сообщений на `/ai/chat`);
        
    - отображение прошлых ответов (`/ai/history`).
        

## 2.3. Личный кабинет (COACH)

- `/coach/dashboard` — обзор (свои сессии, заявки, средний рейтинг).
    
- `/coach/profile` — редактирование профиля тренера.
    
- `/coach/schedule` — расписание тренировок (подтверждение/перенос/отмена).
    
- `/coach/sessions/:id` — детали сессии + форма отчёта.
    
- `/coach/reviews` — список отзывов о тренере.
    

## 2.4. Админ/технический аккаунт (ADMIN)

- `/admin/dashboard` — агрегированные метрики (кол‑во пользователей, заявок, сессий, средний рейтинг).
    
- `/admin/users` — список пользователей с ролями/статусами, действия (смена роли, блокировка).
    
- `/admin/logs` — просмотр `core_action_logs` с фильтрами.
    
- `/admin/db` — read‑only просмотр основных таблиц (простые таблицы/гриды, без SQL‑ввода).
    
- `/admin/ml-import` — форма для указания директории Kaggle CSV, вызывает `POST /ml/admin/load-kaggle-data` и показывает статус/лог.

## 3. UI‑тулкит / дизайн‑система

Смысл «тулкита»: единый набор компонентов и стилей, который:

- лежит в отдельной директории (например, `src/ui` или отдельный package `@app/ui`);
    
- содержит переиспользуемые компоненты:
    
    - базовые: `Button`, `Input`, `Select`, `Checkbox`, `Modal`, `Tabs`, `Card`, `Table`, `Badge`, `Alert`;
        
    - layout: `Page`, `Sidebar`, `TopBar`, `Container`;
        
    - специализированные:
        
        - `StatCard` — карточка с ключевой метрикой;
            
        - `TrendChart` — обёртка над chart‑библиотекой;
            
        - `RoleBadge`, `RankBadge`;
            
        - `CoachCard`, `RequestCard`, `SessionCard`.
            
- Документация: в `FRONTEND_SPEC.md` можно кратко описать эту структуру и указать, что компоненты должны быть максимально статичными (без побочек, вызывающих API), а логика работы с данными — в контейнерных/страничных компонентах.

## 4. Требования к безопасности фронтенда

Фронт сам по себе не может защитить от SQL‑инъекций (это задача бэка), но можно зафиксировать правила, чтобы он **не становился источником дыр**.

- **Нет прямого доступа к БД**:
    
    - фронт общается ТОЛЬКО с HTTP‑API core/auth/ml/llm по HTTPS;
        
    - никакие строки подключения, SQL‑запросы, секреты не хранятся во фронте.
        
- **Хранение токенов**:
    
    - access‑токен в httpOnly cookie или, как минимум, не в открытых глобальных переменных;
        
    - не логировать токены в консоль.
        
- **Валидация и санитация**:
    
    - все вводимые данные (формы, поля чата) проверяются на фронте для UX, но **истинная валидация и авторизация выполняется на бэке**;[](https://nareshit.com/blogs/react-security-best-practices-developers-should-know)​
        
    - нигде не используется `dangerouslySetInnerHTML`, кроме строго проверенных мест с санитацией.
        
- **Защита от XSS/CSRФ**:
    
    - не вставлять в DOM значения, полученные от пользователя, без экранирования;
        
    - использовать защищённые cookie/заголовки для авторизации;
        
    - не полагаться на «скрытые кнопки» как на защиту.
        
- **Отсутствие произвольного SQL**:
    
    - интерфейс `/admin/db` показывает только заранее определённые выборки, **нет поля для ввода SQL** или прямого обращения к БД с фронта.
        
- **Обновление зависимостей и проверка уязвимостей**:
    
    - использовать актуальные версии React и библиотек;
        
    - опционально прогонять SAST/сканеры уязвимостей.

## 5. Логирование на фронте

- Для отладки можно логировать действия пользователя (клики по ключевым кнопкам) в аналитике, но:
    
    - не логировать чувствительные данные (токены, пароли, содержимое приватных советов);
        
    - основное логирование (для аудита) уже реализовано в core‑сервисе (`core_action_logs`).[](https://www.scitepress.org/publishedPapers/2025/133910/pdf/index.html)​
